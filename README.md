# Лабораторная работа 2

## Текст задания

Доработать ИС из ЛР1 следующим образом:
- Добавить в систему возможность массового добавления объектов при помощи импорта файла. Формат для импорта необходимо согласовать с преподавателем. Импортируемый файл должен загружаться на сервер через интерфейс разработанного веб-приложения.
  - При реализации логики импорта объектов необходимо реализовать транзакцию таким образом, чтобы в случае возникновения ошибок при импорте, не был создан ни один объект.
  - При импорте должна быть реализована проверка пользовательского ввода в соответствии с ограничениями предметной области из ЛР1.
  - При наличии вложенных объектов в основной объект из ЛР1 необходимо задавать значения полей вложенных объектов в той же записи, что и основной объект.
- Необходимо добавить в систему интерфейс для отображения истории импорта (обычный пользователь видит только операции импорта, запущенные им, администратор - все операции).
  - В истории должны отображаться id операции, статус ее завершения, пользователь, который ее запустил, число добавленных объектов в операции (только для успешно завершенных).
- Согласовать с преподавателем и добавить в модель из первой лабораторной новые ограничения уникальности, проверяемые на программном уровне (эти новые ограничения должны быть реализованы в рамках бизнес-логики приложения и не должны быть отображены/реализованы в БД).
- Реализовать сценарий с использованием Apache JMeter, имитирующий одновременную работу нескольких пользователей с ИС, и проверить корректность изоляции транзакций, используемых в ЛР. По итогам исследования поведения системы при ее одновременном использовании несколькими пользователями изменить уровень изоляции транзакций там, где это требуется. Обосновать изменения.
  - Реализованный сценарий должен покрывать создание, редактирование, удаление и импорт объектов.
  - Реализованный сценарий должен проверять корректность поведения системы при попытке нескольких пользователей обновить и\или удалить один и тот же объект (например, двух администраторов).
  - Реализованный сценарий должен проверять корректность соблюдения системой ограничений уникальности предметной области при одновременной попытке нескольких пользователей создать объект с одним и тем же уникальным значением.

## Ограничения уникальности

- Название ордена уникально без учёта регистра и пробелов. Смысл: у ордена один командир, двух орденов с одним именем быть не может.
- Координаты (x, y) уникальны, точки общие. Смысл: одна точка пространства соответствует одной записи.
- Полный дубль десантника запрещён. Смысл: защита от повторного ввода и повторного импорта. Реакция: в форме ответ 409, в импорте строка пропускается.

## Пользователи и правила доступа (ЛОР)
Обычные пользователи это командующие. Администраторы это главнокомандующие. Десантники из лабораторной - это подчиненные. 
Командующие руководят орденами, которые они создали. Они добавляют туда своих подчиненных десантников. 
Таким образом только командующий может изменять и удалять свой орден и своих людей. 
Главнокомандующий имеет доступ ко всем орденам и подчиненным. Координаты создать может каждый, а редактировать или удалять только главнокомандующий, то есть они типа общие.

Получаем, что десантника нельзя записать в чужой орден, десантник всегда принадлежит владельцу своего ордена. Поэтому отдельное поле `owner_id` у десантника не нужно. 
Владелец хранится только у ордена, а владелец десантника вычисляется как `marine.chapter.owner`.
Также если администратор создаёт десантника в ордене пользователя A, десантник принадлежит пользователю A. 
Что логично: главнокомандующий может назначить бойца в чужой орден, но подчиняется боец командиру ордена.

### Проблемы
**Проблема 1:**
Ограничения уникальности по заданию проверяются только в коде, в БД их нет. Проверка устроена так: «найти такой же объект (SELECT) → если нет, создать (INSERT)». По умолчанию PostgreSQL работает на уровне READ COMMITTED: транзакция видит только закоммиченные данные. Два запроса одновременно:

```
T1: SELECT — такого ордена нет
T2: SELECT — такого ордена нет   (вставка T1 ещё не закоммичена, T2 её не видит)
T1: INSERT, COMMIT
T2: INSERT, COMMIT              → два одинаковых ордена
```

Блокировки строк тут не помогают: транзакции пишут разные строки. Нарушается условие на множество строк («среди всех орденов нет такого названия»). 

**Проблема 2:**
Администратор читает объект в одном HTTP-запросе (открыл форму), а сохраняет в другом — это разные транзакции. Между ними другой администратор успевает сохранить свои изменения. Никакой уровень изоляции здесь не поможет: транзакция сохранения началась уже после чужого коммита и честно видит актуальные данные. Она просто не знает, что пользователь редактировал устаревшую версию.

### Решения
**Для проблемы 1:**
Сделаем SERIALIZABLE там где проверяется уникальность: создание и изменение ордена, координат и десантника, импорт. Чтение, удаление, вход и история импорта остались на READ COMMITTED. Потому что SERIALIZABLE дорогой.

И важный нюанс: SERIALIZABLE не ставит транзакции в очередь, а отменяет одну из них. Поэтому добавлен автоматический повтор: отменённая транзакция выполняется заново. При повторе она уже видит закоммиченный орден конкурента и отвечает 409 «уже существует».

**Для проблемы 2:**
Была сделана оптимистическая блокировка:
- у десантника, ордена и координат есть `@Version` (колонка `version`); EclipseLink пишет `UPDATE … WHERE id = ? AND version = ?` и увеличивает версию;
- клиент получает `version` вместе с объектом и возвращает её при `PUT`; сервис сравнивает (`service.Versions`): не совпала — **409** «уже изменил другой пользователь»;
- гонку внутри самой транзакции (между проверкой и `UPDATE`) закрывает `@Version`: строка с ожидаемой версией не найдена → `OptimisticLockException` → **409**;
- удаление тоже идёт по версии (`DELETE … WHERE version = ?`): если объект только что изменили — 409, а изменение уже удалённого объекта — 404 или 409, но не «успешные» 200;
- массовая перепривязка (`UPDATE … SET chapter`) обходит `@Version`, поэтому увеличивает версию явно;
- `flush()` в конце изменения — чтобы конфликт проявился внутри метода и превратился в понятный 409, а не в ошибку коммита;
- при сохранении версия увеличивается **всегда** (`LockModeType.OPTIMISTIC_FORCE_INCREMENT`), даже если поля не изменились. Иначе EclipseLink не выполняет UPDATE для «сохранения без изменений», версия не проверяется, и конфликт не обнаруживается.
