# Сценарий JMeter для ЛР2

`spacemarine-lr2.jmx` имитирует одновременную работу нескольких пользователей и проверяет,
что система при этом не нарушает свои правила.

## Где запускать

JMeter запускается **на своём компьютере**. Приложение работает на helios, JMeter обращается
к нему через тот же SSH-туннель, что и браузер. Ставить JMeter на helios не нужно.

```
ваш компьютер                         helios
JMeter ──► localhost:8080 ══SSH══►  Payara :12345 ──► PostgreSQL (pg)
```

Туннель передаёт параллельные запросы параллельно (каждое соединение — отдельный канал),
поэтому одновременность сохраняется.

## 1. Установка (один раз)

1. Нужна Java 8 или новее: `java -version`.
2. Скачать JMeter: https://jmeter.apache.org/download_jmeter.cgi → **Binaries** → `apache-jmeter-5.6.3.zip`.
3. Распаковать в папку без пробелов и кириллицы в пути.
4. Запустить: Windows — `bin\jmeter.bat`, macOS/Linux — `bin/jmeter`.

## 2. Подготовка приложения

1. (Рекомендуется) пересоздать базу, чтобы в ней не было старых данных:
   `psql -h pg -d studs -f schema.sql` на helios.
2. Запустить Payara на helios, как обычно.
3. Открыть туннель на своём компьютере:
   `ssh -p 2222 -L 8080:localhost:12345 sXXXXXX@helios.cs.ifmo.ru`
4. Убедиться, что сайт открывается: http://localhost:8080/spacemarine/

## 3. Запуск в интерфейсе JMeter

1. **File → Open** → `jmeter/spacemarine-lr2.jmx`.
2. В корне дерева (Test Plan) — параметры. Значения по умолчанию подходят для туннеля
   `localhost:8080` и контекста `spacemarine`. Если порт другой — поменяйте значение `PORT`
   прямо там (например, `${__P(port,8080)}` → `${__P(port,9090)}`).
3. Нажать зелёную кнопку **▶ Start**. Группы потоков выполняются **по очереди**
   (так настроен Test Plan), весь прогон занимает меньше минуты.
4. Результаты:
   * **View Results Tree** — каждый запрос; красные — не прошли проверку.
     Выберите запрос → вкладки *Request* (что отправили) и *Response data* (что ответил сервер).
   * В самом конце — **«ИТОГ по кодам ответов»**: откройте его *Response data*, там сводка
     по всем группам и список нарушений.
   * **Summary Report** — количество запросов, время ответа, процент ошибок.
5. Перед повторным запуском: **Run → Clear All** (метёлка с двумя щётками).
   Каждый прогон использует новую метку `RUN`, поэтому данные разных прогонов не пересекаются.

## 4. Запуск без интерфейса — для отчёта

Из папки `jmeter` проекта (`<JMETER>` — куда распаковали JMeter):

```bash
<JMETER>/bin/jmeter -n -t spacemarine-lr2.jmx -l before.jtl -e -o report-before -Jusers=10
```

* `-n` — без интерфейса, `-l` — сырые результаты, `-e -o` — HTML-отчёт в папку `report-before`
  (папка должна не существовать). Откройте `report-before/index.html`.
* Параметры: `-Jusers=20` (сколько одновременных пользователей), `-Jloops=3`, `-Jport=8080`,
  `-Jhost=localhost`.
* Сводка «ИТОГ» печатается и в `jmeter.log`.

## 5. Что делает каждая группа

| Группа | Что имитирует | Корректное поведение | Требование задания |
|---|---|---|---|
| 0. Подготовка | admin1 создаёт общий орден, десантников A и B; регистрируется «общий» пользователь | — | — |
| 1. Работа N пользователей | каждый регистрируется и 3 раза: смотрит список, создаёт десантника, открывает, изменяет, импортирует файл из 2 записей, удаляет, смотрит историю импорта | все ответы успешные | создание, редактирование, удаление, импорт |
| 2. Два администратора изменяют A | оба читают десантника, затем **одновременно** сохраняют разные изменения | ровно один 200, второй 409 | несколько пользователей обновляют один объект |
| 3. Изменение и удаление B | admin1 изменяет, admin2 **одновременно** удаляет | удаление 204; изменение 200 (успело раньше) или 404/409; нет 5xx | обновление и удаление одного объекта |
| 4. Гонка орденов | N пользователей одновременно создают «JM race …» / «JM RACE …» | один 201, остальные 409; в БД один орден | уникальность при одновременном создании |
| 5. Гонка координат | N пользователей одновременно создают одну точку | один 201, остальные 409 | то же |
| 6. Гонка импорта | N пользователей одновременно импортируют файл с одним новым орденом | один импорт успешен, остальные 409 (орден уже чужой); 3 десантника | импорт + уникальность |
| 7. Импорт из двух окон | один пользователь одновременно загружает один файл дважды | первый добавил 3, второй 0 (дубли пропущены) | то же |
| 8. Гонка дубля | N окон одного пользователя одновременно создают одинакового десантника | один 201, остальные 409 | то же |
| 9. Проверка результатов | читает ордены, координаты, десантников и коды ответов групп 2–8 | нет красных строк | — |

«Одновременно» обеспечивает **Synchronizing Timer**: он задерживает потоки группы,
пока не соберутся все, и отпускает их разом.

## 6. Чего ждать сейчас (до исправления изоляции)

Сейчас транзакции работают на уровне PostgreSQL по умолчанию (READ COMMITTED), а в модели
нет версий объектов. Это исходное состояние для исследования:

* **Группа 2 упадёт всегда**: оба администратора получат 200 — потерянное обновление
  (второй молча перезаписал изменения первого).
* **Группа 3**: изменение может получить 200, хотя объект уже удалён — изменение «потерялось».
  Сводка показывает коды обоих запросов; нарушением считаются только ошибки 5xx.
* **Группы 4–8** — гонки «проверил, потом записал». Проявляются не при каждом запуске:
  запустите 3–5 раз, при необходимости увеличьте `-Jusers=20` или `30`. Признак — несколько
  ответов 201 и сообщения «создано орденов … — 2, ожидался 1».

Для отчёта сохраните:
1. HTML-отчёт и скриншот «ИТОГ по кодам ответов» с нарушениями;
2. результат SQL-запросов на helios, показывающих дубли, которых не должно быть:

```sql
SELECT lower(name), count(*) FROM chapter GROUP BY 1 HAVING count(*) > 1;
SELECT x, y, count(*) FROM coordinates GROUP BY 1, 2 HAVING count(*) > 1;
SELECT lower(name), coordinates_id, chapter_id, health, height, count(*)
  FROM space_marine GROUP BY 1, 2, 3, 4, 5 HAVING count(*) > 1;
```

## 6а. После исправления

Пересоберите war и снова запустите сценарий (базу можно не пересоздавать — у каждого прогона своя метка):

```bash
<JMETER>/bin/jmeter -n -t spacemarine-lr2.jmx -l after.jtl -e -o report-after -Jusers=10
```

Ожидается: в «ИТОГ по кодам ответов» — «Нарушений нет»; в группах 2, 4–8 ровно по одному успешному
ответу, остальные 409; в группе 1 — все ответы успешные. В логе Payara будут строки
«ChapterService.create: конфликт сериализации (…), повтор 2 из 8» — это PostgreSQL отменил одну из конкурирующих
транзакций, а приложение её повторило. Попробуйте `-Jusers=20` и `30`.

Если в группе 1 изредка появляется 409 «Конфликт одновременных изменений» — это исчерпаны повторы
при сильной нагрузке; поведение корректное (данные не испорчены), но можно увеличить
`MAX_ATTEMPTS` в `SerializableExecutor`.

## 7. Если что-то не так

| Симптом | Причина |
|---|---|
| Все запросы — `Connection refused` | не открыт туннель или Payara не запущена |
| «Подготовка не удалась: нет TARGET_A…» | admin1 не вошёл: в базе нет администраторов (не запущен новый schema.sql) или пароль не `admin` |
| Группа 1 падает на импорте с 404 | старая версия war без `/api/imports/upload` |
| Много 500 и в логе Payara `too many connections` | уменьшить `maxPoolSize` в `DataSourceConfig` или `-Jusers` |
